QR Studio 開発記録

【2026-07-11】プロジェクト開始

■ 受領したプロンプト概要
- サービス名: QR Studio（「考えなくても、最高品質のQRコード。」）
- Frontend: Next.js(App Router) + React + TypeScript + Tailwind CSS + PWA、Vercel Freeにデプロイ
- Backend: Python FastAPI、Google Cloud Run（min-instances=0）にデプロイ
- Backend の役割は「APIサーバー」ではなく「QR Quality Engine（品質保証エンジン）」
- 完全Stateless設計（URL・画像・ログを一切保存しない）
- セキュリティ（CSP/HSTS等ヘッダー、入力検証、SVGサニタイズ、レート制限）
- QR生成・デザイン編集・ロゴ追加・出力サイズプリセット・自動品質補正・PWA・パフォーマンス最適化・テスト・デプロイまで一貫実装

■ 採用アーキテクチャ（設計理由は README.md / docs/architecture.md に記載）
- QRコードのレンダリングはクライアントサイド（qr-code-styling）でリアルタイムに実施し、
  ネットワーク往復なしで即座にプレビューできるようにする。
- FastAPI側は「品質診断＋自動補正パラメータの算出」のみを担当。
  画像はBase64でリクエストボディに載せて渡し、処理後は一切保存せずメモリ上で破棄する。
- 3種類のデコードエンジン（OpenCV QRCodeDetector / pyzbar(zbar) / zxing-cpp）で
  クロス検証し、全てのデコーダーで読み取れることを保証する。
- 品質診断結果はユーザーに見せず、内部の自動補正ループ（フロントのカスタムフック）が
  補正後パラメータで再生成→再検証を収束するまで自動で繰り返す。

■ 重大な環境問題の調査と原因特定(重要・今後の参考用)
症状: `npm install`実行時、esbuild/unrs-resolver/core-js等のpostinstallスクリプトが
ことごとく `STATUS_ACCESS_VIOLATION`(0xC0000005)でクラッシュ。さらに`--ignore-scripts`で
インストール後、`node -e "require('react')"` や `tsc --version`、`next --version`など、
node_modules配下のパッケージをrequireする操作が軒並み同じ理由でクラッシュした。
一方、`console.log(1+1)`のようなrequireを伴わない処理や、Pythonのpytest/ruffは
同じプロジェクトディレクトリ内で問題なく動作した。

切り分けの結果、原因はプロジェクトパスに含まれる日本語フォルダ名
("AIエンジニア"、"QR自動作成ツール")であると判明。同じnode_modulesを
英数字のみのパス(例: %TEMP%\qr-frontend-build)にコピーして実行すると、
`npm install`(postinstallスクリプト含む)・`tsc`・`eslint`・`next build`・`vitest`
全てが正常に動作した。Windowsジャンクション(シンボリックリンク)経由でも
実体パスが日本語のままだと再現したため、シンボリックリンクでの回避は不可。

結論: これはNode.js(v22.12.0)がこのWindows環境で非ASCIIパスをnode_modulesの
require解決時に正しく扱えない、環境固有の問題であり、コードの不具合ではない。
Vercel等のLinuxビルド環境や、英数字パスでのローカル開発では発生しない。
本セッションでは英数字の一時ディレクトリにコピーしてビルド・テスト・lintを
実施し、修正が必要だった実際のコード上の問題(下記)は本体のプロジェクトに反映した。

■ 上記の検証中に見つかった実コードの修正
- app/page.tsx: `next/dynamic`の`ssr:false`はServer Componentで使用不可(Turbopackが拒否)

- hooks/useQualityAssurance.ts: `react-hooks/set-state-in-effect`ルールにより、

- hooks/useQrStylingInstance.ts: getRawDataの返り値型(Blob | Buffer)の型不整合を修正。
- lib/security/fileValidation.ts: jsdomテスト環境でBlob#arrayBuffer/textが未実装だったため、
  FileReaderベースの読み取りに変更(実ブラウザでもより広く互換性のある実装になった)。
- eslint設定をESLint9のflat config形式(eslint.config.mjs)に全面移行
  (eslint-config-next 16はexports経由でflat config配列を直接提供している)。

【2026-07-11】実ブラウザ(Playwright)での動作確認と、そこで発見した3件の実バグ修正
ユーザーから「実際にnpm run devを動かして画面を見せて」と依頼されたため、chromium-cliが
本環境に無かったのでPlaywright(chromium)をASCIIパスの作業コピーに導入し、
バックエンド(実フォルダの.venvから直接起動、Pythonは日本語パスでも問題なし)と
フロントエンド(ASCIIコピー上でnpm run dev相当)を実際に起動し、ヘッドレスブラウザで
URL入力→QR生成→デザイン変更→ダウンロードボタン活性化までを操作して検証した。
この過程で以下の3件の実際の不具合を発見し、本体のソースに修正を反映した:

1. next.config.mjsのCSPが本番用の厳格な設定のまま開発時にも適用されており、
   `script-src`に`unsafe-eval`が無いため、Reactの開発モードが内部で使うeval()が
   CSP違反でブロックされ、開発サーバーが常にエラー画面(eval() is not supported)に
   なっていた。
   → 修正: `NODE_ENV !== "production"`の時のみ`'unsafe-eval'`を追加するよう変更。

2. lib/qr/qrStylingClient.tsで、ロゴが無い場合に`imageOptions: undefined`を
   明示的にオプションオブジェクトのキーとして渡していたため、qr-code-styling内部の
   デフォルト値マージ処理が壊れ、`Cannot read properties of undefined (reading
   'hideBackgroundDots')`で初回描画時に必ずクラッシュしていた。
   → 修正: ロゴが無い場合は`image`/`imageOptions`キー自体を省略する(スプレッド構文で
   条件付加)よう変更。

3. hooks/useQualityAssurance.tsで、品質チェックのeffectのトリガーに「非デバウンスの
   isUrlProvided」と「デバウンス済みのdesign(expected_payloadの実データ)」という
   異なる基準の値を混在させていたため、URL入力直後の一瞬だけ
   `isUrlProvided=true`だが`debouncedDesign.url`はまだ空文字、という状態で
   バックエンドへ`expected_payload: ""`のリクエストを送ってしまい、
   Pydanticのmin_length=1バリデーションで422になる競合状態(race condition)が
   実際に発生することを確認した(ブラウザのconsoleエラーとバックエンドのアクセスログで
   確認)。
   → 修正: effectのガード条件を`debouncedDesign.url`から導出した
   `debouncedUrlProvided`に統一し、基準のずれを解消。

■ 修正後の最終確認
- 上記3件を修正後、Playwrightでの一連の操作でconsoleエラー0件、バックエンドの
  quality-checkは200(補正不要)で完了、ダウンロードボタンが活性化することを確認。
  ドット形状を「ラウンド」→「クラシック」に変更した際、QRコードの見た目が
  実際に切り替わることも拡大スクリーンショットで確認済み。
- 検証に使ったPlaywright・作業用コピーはセッション終了時に削除し、本体には残していない
  (package.jsonにplaywrightは追加していない。デモ専用の一時的な導入)。

【2026-07-11】ユーザーがローカルで実際に触った上でのフィードバック対応
ユーザー自身がローカルでnpm run devを動かして操作した結果、以下3点の指摘を受けた。

1. 「グラデーションをオフにしてもグラデーションがついたままになっている」
   → 実際に再現・原因調査した。qr-code-stylingの`update()`は内部で差分マージしか
   行わないため、新しいdotsOptionsに`gradient`キーが存在しない(グラデーションOFF時)
   場合、以前設定した古いgradientの値が消えずに残ってしまう既知の挙動だった。
   ロゴを外す場合の`image`/`imageOptions`にも同種の問題が起こり得ると判断し、
   hooks/useQrStylingInstance.ts を「update()で差分反映」から
   「design変更のたびにコンテナをクリアしてインスタンスを作り直す」方式に変更して解決。
   Playwrightで on→offを実機検証し、offにした際に単色に戻ることを確認済み。

2. 「縦に長く、見づらいので見やすいようにして」
   → デザイン編集・ロゴ追加・出力サイズの3つの独立したカードが縦に積み上がっていたのが
   原因。components/ui/Tabs.tsx を新規作成し、この3つを1枚のカード内のタブ
   (デザイン/ロゴ/サイズ)に統合。ダウンロードカードのみ独立して常時表示のまま残した。
   これによりページの縦の長さが大幅に短縮され、QRプレビューとほぼ同じ高さに収まることを
   スクリーンショットで確認。

3. 「もっとレパートリーが欲しい。ポップとか。」
   → lib/qr/stylePresets.ts と components/qr/StylePresets.tsx を新規作成し、
   「ミニマル・ポップ・オーシャン・ビジネス・ナチュラル・ダーク」の6種類の
   スタイルプリセット(色・グラデーション・ドット形状・四隅デザインの組み合わせ)を
   ワンクリックで適用できるようにした。デザインタブの先頭に配置。
   hooks/useQrDesign.ts に applyStylePreset を追加。

修正後、tsc/eslint/vitest(22件)/next buildを再実行し全て通過を確認。
Playwrightでの実機検証(グラデーションOFF反映、ポップ適用、タブ切り替え)も
console エラー0件で完了。

【2026-07-11】「ダーク」の差し色調整 と「全面テーマ」機能の追加、および
実装中に発見した4件の重大な補正ロジック不備

ユーザーから「ダークの差し色が強い」との指摘、および「QR全体がテーマの世界観になる
機能(桜・海・宇宙・猫・ゲーム・和柄など)が欲しい」との要望を受けた。ChatGPTとの
相談を踏まえ、ユーザーは「大胆な見た目(リスクあり)」を選択したが、その後
「安全と分かっているパターンだけを選べるようにしては」という提案があり、
連続スライダーではなく事前検証済みの3段階(濃い→標準→控えめ)+テーマオフの
「はしご」方式を採用することにした。

■ 実装
- lib/qr/themes.ts: 6テーマ(桜/海/宇宙/猫/ゲーム/和柄)の背景パターン(SVG)と
  QR配色を定義。
- lib/qr/themeComposer.ts: QR画像(透明背景でエクスポート、無加工)をテーマ柄の
  上に重ねて合成するSVGを生成。QRの暗いモジュールは一切変更しない。
- qrStylingClient.ts: テーマ使用時はQRの背景を透明にして書き出すよう変更。
- useQrDesign.ts: applyTheme(大胆=intensity2を既定に設定)、
  applyThemeIntensityStepDown(2→1→0→テーマオフの4段階はしご、
  最終手段では配色も黒/白にリセット)を追加。
- useQualityAssurance.ts: 全面テーマ使用時は合成後の最終画像を検証し、
  デコード失敗時はまずテーマの濃さを1段階下げてから他の補正を試すよう変更。
  MAX_ITERATIONSを5→10に増やし、複数の補正軸(テーマ段階・EC・Quiet Zone・
  四隅形状・コントラスト)を組み合わせても収束しやすくした。

■ 実機検証(ダウンロード→3エンジンデコード)で発見した4件の重大な不備
1. コントラスト判定が「アンチエイリアシング」に弱かった
   通常サイズ(640px)の実際のブラウザ描画QR(丸みのあるドット)で、縁の
   アンチエイリアシングピクセルが「最悪ケース評価」に混入し、黒/白の
   理想的なQRですら不合格判定になっていた。dark cluster/light clusterの
   min/maxではなくパーセンタイル(上下5%を切り捨て)に変更して解決。
2. コントラスト不足の補正が実質何もしていなかった
   correction_engine.build_correctionsは contrast_ok=False でも
   size_px等を一切変更しておらず、同じ補正を延々返し続ける実質無限ループに
   なっていた。「モジュールが小さい+丸形状→アンチエイリアシングでコントラスト
   低下」が根本原因と判明したため、contrast_ok=Falseの際にsize_pxを1.5倍に
   増やす補正を追加。
3. サイズが上限(4096px)に達してもなお解決しない場合の対策が無かった
   極端に長いURL(モジュール数57)ではサイズ拡大だけでは解決しないケースがあり、
   QrDesignParamsに`dot_style`(square/other)を追加し、サイズが上限に達した
   場合の最終手段としてドット形状をsquareへフォールバックする補正を追加。
4. フロントの補正適用ロジックが「コントラスト補正」と「構造的補正」を
   排他的に扱っていた(片方適用したら即returnして、同じラウンドでもう片方を
   適用しない)ため、両方に問題がある場合に収束が遅れていた。両方を同じ
   ラウンドでまとめて適用するよう修正。

■ 検証方法と結果
Playwrightで実際に全6テーマ・全6スタイルプリセット・全3フレームテンプレートを
ダウンロードし、OpenCV / pyzbar / zxing-cpp の3エンジン全てで正しくデコードできる
ことを個別に確認(通常のURL長で全パターンOK)。さらに意図的に長いURL

収束するまでdisabled状態を保つため、実際のユーザーが未収束の状態を

【2026-07-11】「テーマ」を「背景」として色と分離する大幅リデザイン

ユーザーから以下のフィードバックを受けた:
1. フレーム適用で背景パターンが消える
2. テーマ選択が何度もリセットされ、1回で切り替わらない
3. テーマ設定後に色を変えて良いか不安
4. 「テーマ」ではなく「背景」として設定し、QRの色は読み取りやすい範囲だけ選べるようにしては
5. 背景パターンの種類を増やしたい
6. 読み取りやすさを最優先に

ユーザー提案(4)を採用し、以下のように再設計した。

■ 設計変更
- 「テーマ」概念を廃止し「背景」に置き換え。背景パターンはQRの色(foregroundColor/
  gradient/cornerAccentColor)に一切影響しない、純粋な装飾のみになった
  (lib/qr/backgroundPatterns.ts、旧themes.tsを置き換え)。
- QRの色(前景色・グラデーション・四隅の差し色)は自由入力を廃止し、
  事前に白背景に対して4.5:1以上のコントラストを検証済みの色/グラデーションのみ
  選べるパレット方式に変更(lib/qr/safeColors.ts、components/ui/SwatchPicker.tsx)。
  背景色も白/ソフトグレー/クリームの3色のみに限定し、どの組み合わせでも
  コントラスト基準を満たすことを確認済み。
- フレームと背景パターンを併用可能にした。両方選択時は、フレームの土台(白い
  カード部分)に背景パターンを敷き込んで合成する(lib/qr/frameTemplates.tsの
  各ビルダーが`backgroundFill`引数を受け取れるよう変更、lib/qr/patternComposer.ts
  で統合)。これによりフレーム選択時に背景が消える問題を解消。
- 背景パターンを6種類→12種類に拡充(桜/海/宇宙/猫/ゲーム/和柄/雪/紅葉/花火/
  ハート/音符/森)。色と分離したことで、各パターンごとに安全な色を選定する
  必要がなくなり、種類を増やしやすくなった。
- 「何度もリセットされる」問題は、色とパターンの結合が原因で自動補正ループが
  不安定になっていたことが根本原因だったため、この分離により解消される設計。

■ ファイル変更
- 新規: lib/qr/backgroundPatterns.ts, lib/qr/safeColors.ts, lib/qr/patternComposer.ts,
  components/ui/SwatchPicker.tsx, components/qr/BackgroundPanel.tsx,
  hooks/useComposedPreview.ts
- 削除: lib/qr/themes.ts, lib/qr/themeComposer.ts, hooks/useFramedPreview.ts,
  hooks/useThemedPreview.ts, components/qr/ThemePanel.tsx

   検出に失敗し、zxing-cppのみ成功した。プレーンな正方形モジュールでも同様に
   失敗することを確認しており、色の反転そのものが根本原因(コントラスト比の

3. **グラデーションの明るい側の色が背景とのコントラスト不足**

2026-07-11: フレームテンプレートの追加・テキストボックスの表示切替・
バッジデザインの刷新
====================================================================

■ 受領したプロンプト
「フレームのテンプレートも増やしてほしい。テキストboxはオンとオフで選べる
ようにしたい。たとえば吹き出しだとテキスト部分を出すか、消して吹き出しの身に
なるようにしたい。後、バッジのテンプレートがちょっとよくわからなかった。
バッジに見えない。」

■ 対応方針
1. 「テキストボックス」オン/オフ切り替えを全フレーム共通のトグルとして追加。
   ただし「消す」動作の意味はテンプレートによって使い分けた:
   - 吹き出し: ユーザーの例の通り、上部のラベル(角丸タグ+テキスト)を
     要素ごと非表示にし、バブル本体+しっぽだけの「身」にする。
   - リボン: 帯自体がテンプレートの主役の装飾なので、帯の形は残したまま
     中の文字だけ消す(空の帯として成立する)。
   - バッジ(新デザイン): 盾の先端の三角形はシルエットを構成する必須パーツ
     なので残し、中の文字だけ消す。
   - チケット/ポラロイド: スタブ/キャプション帯を残したまま文字だけ消す
     (空白でも本来の形として自然)。
   - タグ: キャプション帯は付加的な要素のため、吹き出しと同様に帯ごと消す。
2. バッジテンプレートを「角丸四角+四隅の点+上に重なる丸ラベル」という
   ただの装飾過多なカードから、「盾(シールド)型」に全面刷新。
   上部は角丸四角(QR収容領域)、下部中央に尖った先端(差し色で塗り分け)、
   四隅にリベット風の点、内側に破線のステッチ風の縁取りを追加し、
   一目でバッジ/認証シールとわかるシルエットにした。QRは常に上部の
   四角い領域にのみ配置するため、先端の形状は読み取りに一切影響しない。
3. 新規フレームテンプレートを3種類追加:
   - チケット: 半券風。SVGのmask機能で左右の切り欠き(半円の穴)を実際に
     透過させ、点線の切り取り線+縦書きのスタブテキストを配置。
   - タグ: 値札/荷札風。上部に紐を通す穴付きの尖った「頭」をmaskで
     くり抜き、下部にキャプション帯(トグルで表示/非表示)を配置。
   - ポラロイド: インスタント写真風。上下左右のうち下だけ太いキャプション
     帯にする定番比率、斜体テキストで手書き風の雰囲気を出した。

1. ロゴ画像アップロード時、Canvasで中央基準の正方形にクロップ+四角/丸の

2. ドラッグでパン、スライダーで拡大縮小できる手動トリミングUI

インストール可能と判定していないことを意味する。

調査の結果、`public/sw.js`に重大な設計上の不具合を発見した:
fetchハンドラが"/"と"/manifest.webmanifest"を含む全リクエストに対し
「キャッシュ優先(cache-first)」戦略を採用していたため、一度でもこの
サイトを訪問しService Workerがアプリシェルをキャッシュした端末は、
それ以降何度デプロイし直しても常に古い"/"・古いmanifestを見続ける
(Service Workerはsw.js自身のバイト内容が変化しない限り再インストール
されず、installイベント=再キャッシュが起きないため)。本プロジェクトは
この日だけでも複数回デプロイを重ねており、ユーザーの端末は開発初期の
(PWA設定が未完成だった頃の)"/"やmanifestをずっとキャッシュから
返され続けていた可能性が高いと判断した。

■ 対応
`public/sw.js`を修正:
- "/"と"/manifest.webmanifest"のみ「ネットワーク優先
  (network-first、オフライン時のみキャッシュにフォールバック)」戦略に
  変更。それ以外の静的アセット(_next/static配下のハッシュ付きファイル等)
  は従来通りキャッシュ優先のまま(ファイル名自体がビルドごとに変わるため
  問題ない)。
- `CACHE_NAME`を"qr-studio-shell-v1"→"v2"に変更。sw.js自体のバイト内容が
  変わったことで、既存訪問者のブラウザも次回アクセス時に新しいService
  Workerを検知・インストールし、古いキャッシュ(v1)を破棄するようにした。

■ 検証
スクラッチパッド配下のASCIIパスコピー経由で`next build`を実行し、
sw.js変更を含めてclean(エラー無し)であることを確認。

■ 教訓(重要)
- PWAのService Workerで"/"やmanifestをキャッシュ優先にすると、
  既存訪問者は「Service Worker自体が更新されない限り」永遠に
  最初にキャッシュした時点の内容を見続けてしまう。これはService
  Workerの仕様(sw.js自身のバイト差分でのみ更新検知)に起因する
  典型的な落とし穴であり、アプリシェル(HTML本体・manifest)は
  network-first、内容がハッシュ化された静的アセットのみ
  cache-firstにする、という使い分けが必要だった。
- 「デプロイしたのに変化が反映されない」系の不具合は、サーバー側
  (Vercel/Cloud Run)の状態だけでなく、クライアント側のService Worker
  キャッシュが原因であるケースも疑うべき。特にPWA対応後は、キャッシュ
  戦略そのものにバグがあると「新機能を追加しても一部ユーザーには
  一切届かない」という気づきにくい形で症状が出る。
