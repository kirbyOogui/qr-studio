# QR Studio — システムアーキテクチャ設計

## 1. コンセプトとアーキテクチャ上の帰結

「考えなくても、最高品質のQRコード。」を実現するには、ユーザーが待たされず・迷わず、
かつ裏側で品質が保証されている必要がある。この2つの要求（速さ／品質保証）を両立するため、
QRコードの**生成**と**品質保証**を明確に分離した。

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│      Frontend (Vercel)       │        │   Backend (Cloud Run)         │
│  Next.js App Router / React  │        │   FastAPI = QR Quality Engine │
│                               │        │                                │
│  URL入力                     │        │  ・OpenCV / pyzbar / zxing-cpp │
│   ↓                           │        │    の3エンジンでデコード検証   │
│  qr-code-styling で           │  POST  │  ・コントラスト解析            │
│  クライアント側に即時レンダリング │ ────▶ │  ・Quiet Zone解析              │
│   ↓                           │ 画像は │  ・ロゴ被覆率解析               │
│  品質チェックAPI呼び出し       │ Base64 │  ・解像度／モジュールサイズ解析  │
│   ↓                           │ ◀──── │  ↓                             │
│  補正パラメータを適用して       │ 補正案 │  補正パラメータを返却          │
│  再レンダリング（自動・非表示） │        │  （スコアや専門用語は返さず、    │
│   ↓                           │        │   "corrections" のみ返す）      │
│  読み取り可能と判定されたQRのみ │        │  レスポンス後、画像はメモリから  │
│  表示・ダウンロード可能に       │        │  即時破棄・一切ログ出力しない    │
└─────────────────────────────┘        └──────────────────────────────┘
```

### なぜQR生成をフロントエンドで行うのか

- 色・形状・グラデーションなどの編集は「リアルタイム反映」が要件であり、
  デザイン変更のたびにバックエンドへ往復すると体感速度が悪化し、Cloud Runの
  コールドスタート影響も強く受けてしまう。
- QRコード自体の生成（誤り訂正符号の計算・モジュール配置）は暗号学的処理ではなく、
  ブラウザで完結できる軽量な処理であるため、クライアントで行うのが合理的。
- バックエンドは「本当にサーバーでしかできないこと」＝**複数の実績あるデコードエンジンによる
  客観的な読み取り検証**に専念させる。これによりCloud Runの呼び出し回数も最小化でき、
  無料枠運用（min-instances=0）と相性が良い。

### 品質保証ループ（自動補正）

1. フロントエンドが現在のデザイン設定でQRを生成（Canvas/SVG）。
2. 生成画像をPNGとしてエクスポートし、Base64で `/api/v1/qr/quality-check` に送信。
3. バックエンドが3エンジンでデコードし、元のURLと一致するか検証。合わせて
   コントラスト比・Quiet Zone幅・ロゴ被覆率・解像度を解析。
4. 問題があれば、ユーザーには一切通知せず「修正済みの設定値」を返す
   （例: Error Correctionを `M`→`Q`へ、Quiet Zoneを4モジュール→6モジュールへ、
   ロゴサイズを28%→20%へ、出力サイズを512px→768pxへ）。
5. フロントエンドは補正値を適用して再レンダリングし、再度検証（最大5回まで収束を試行）。
6. 全デコーダーで一致・各種指標が閾値内になった時点で「読み取り可能」と確定し、
   ダウンロードボタンを有効化する。この間ユーザーには
   「品質を確認しています…」という自然なローディング演出のみを見せる。

### Stateless原則の実装方法

- バックエンドはリクエストを **メモリ上の一時変数のみ** で処理し、レスポンス送出後に
  参照を破棄する（ファイル書き込み・DB・キャッシュ・外部ストレージを一切使用しない）。
- アクセスログ／アプリケーションログには、URLやQR画像のペイロードを**フィールドとしても
  含めない**ミドルウェアを実装（`app/core/logging.py`）。ログに残るのはメソッド・パス・
  ステータスコード・処理時間・匿名化されたクライアント識別子（レート制限用途、URLは含まない）のみ。
- サーバーはユーザーが入力したURLに対して**アウトバウンドで一切アクセスしない**
  （デコード結果の文字列比較のみで検証し、実際にURLを開かない）。これはSSRF対策にも直結する。
- フロントエンドはCookie・LocalStorage・SessionStorageにURLやQR設定を保存しない
  （PWAのオフラインキャッシュは静的アセットのみを対象とし、ユーザー入力は対象外）。

## 2. デプロイアーキテクチャ

- **Frontend**: Vercel Free。Next.jsのEdge Middlewareでセキュリティヘッダーを付与。
  画像最適化・Tree Shaking・Code Splittingにより Lighthouse 95+ を狙う。
- **Backend**: Google Cloud Run。`min-instances=0` でコスト最小化し、コールドスタートは
  フロントエンドのローディング演出で吸収する。CPU割り当ては「リクエスト処理中のみ」、
  同時実行数は品質チェックのCPU負荷（画像デコード）を踏まえて適切に制限する。
- 両者の通信は HTTPS のみ。CORSはVercelの本番ドメインのみ許可。

## 3. 将来のAI機能拡張を見据えた設計

- Backendの `app/services` は「品質診断」「補正計算」「デコード」を独立したサービスクラスに
  分割しており、将来「AIによるロゴ配置提案」や「AIによるデザイン推薦」を追加する際は
  `app/services/ai_*.py` を追加し `api/v1/endpoints` にルーターを1つ足すだけで拡張できる。
- Frontendの `features/qr-studio` はドメインロジックを持つ機能単位のディレクトリとして分離。
  将来 `features/ai-design-assistant` のような新機能を追加しても既存機能に影響しない。
